# Model design discussion before the preliminary fit

Status: proposal for discussion, 8 September 2026. No model equation, dynamics,
residual architecture, policy rate or fitting configuration has been changed
by this document. The user explicitly requested design review before fitting.

Implementation update: the nominal origin-plus-attitude engine is now available
as a standalone, unfitted module. See [its exact equations and limitations](NOMINAL_DRONE_POSE_RESPONSE.md).
It uses delayed PD/feedforward translation, a frozen pre-hover compensation,
critically damped attitude response and explicit alignment provenance. It is not
yet a selected/fitted replacement in the existing PPO or FullState UI path.

The user subsequently agreed to proceed and asked for the first step. Implemented
the causal pose initializer in `experimental_data/drone_pose_initialization.py`
and ran a read-only three-whip audit in
`runs/audits/20260908-043308-495356-drone-pose-initialization/`. No nominal dynamics
or NN fitting occurred. The initializer supplies last measured tracked-origin
P/R, past-only estimates of V and angular velocity in the tracked frame, and
derived attachment P/V. It does not infer firmware body axes or controller
integral state. Pre-hover measured pose and command histories are retained for
the next model's initialization; hidden controller state must not be silently
invented as an observation.

Over the actually observed CSV maneuvers, orientation changes by 38.13–39.01
degrees relative to the initial measured pose, changing the rigid attachment
offset by 3.68–3.77 cm. These are relative orientation/geometry diagnostics, not
absolute body tilt or the full prediction error. Estimated initial translation
speeds are 0.0142–0.0284 m/s. Initialization occurs at the last measurement before
an onset-minus-100-ms cutoff, without extrapolating to maneuver onset; this
preparation margin does not verify hardware clock alignment. The future rollout
must advance from that timestamp through the known pre-hover command stream.
Eleven targeted CPU tests passed on Windows 11, including future-data exclusion,
quaternion sign invariance, analytic rotating-offset P/V and invalid-history rejection.

## Three quantities to keep separate

1. Virtual force-policy trajectory: generated by the point-mass/cable simulator.
2. Desired tracked-origin P/V/A trajectory: the actual FullState command sequence.
3. Predicted real tracked-origin pose and cable motion: the execution model output.

The same commanded trajectory drives both the modeled execution and the real
controller. The command reference is fixed before execution. The onboard
controller continues to use state feedback. Consequently, the drone response
model represents the loaded vehicle, estimator/controller response and effective
command timing together. It does not receive the virtual policy force as though
that were measured physical motor thrust.

Policy improvement should be scored using the predicted executed cable motion.
Export the desired reference used in that prediction. Exporting the predicted
actual trajectory instead would apply the learned response a second time.

## Reference points and geometry

O is the top cf_7 tracking origin, A the underside attachment, and T the tracked
rigid-body frame. The measured orientation R maps T into the world frame.

    p_A = p_O + R r

r is the existing rigid offset, with approximately -55 mm vertical component.
The attachment-to-C1 flexible span is a separate 63 mm arc. The current lateral
offset estimates remain calibrated quantities, not newly measured geometry.
Neither O nor A is established as the center of mass.

During fitting, measured R reconstructs the measured attachment. During a
predictive rollout, R must be predicted from the initial state and commands.
Future measured R is never provided to the prediction. If attachment velocity
is needed, include R(omega_T cross r); second derivatives additionally require
angular acceleration and centripetal terms.

The present point-mass generator has no orientation trajectory. Its constant
initial-offset conversion can be retained as an explicitly defined *command
generation rule*: p_d,O = p_virtual,A - R_initial r, with unchanged V/A. This
does not promise that the actual attachment follows p_virtual,A during tilt.
A claim of exact dynamic reference conversion would instead require a desired
orientation trajectory and its angular derivatives. Do not use future actual
orientation to perform that inverse conversion.

Historical commands remain exactly as logged even if their original exporter
used a different reference convention. Proposed future conversions must not
be applied retrospectively to the flight inputs used for fitting.

## Proposed preliminary drone model

Use an effective FullState response model at O with explicit attitude prediction.
Keep it low dimensional because only three nearly repeated whips are eligible
for drone fitting. A detailed independently identified motor, inertia, estimator
and controller model is not supported by these observations.

The translational backbone can start from delayed command errors:

    a_base = Kp (p_d(t-d) - p_O) + Kd (v_d(t-d) - v_O)
             + Ga a_d(t-d) + b
    a_pred = a_base + delta_a_drone

A small response state may model acceleration lag rather than hiding all memory
in the NN. Choose lag versus pure effective delay using identifiability and
whole-maneuver prediction checks; do not freely fit several interchangeable
delays/lags. These are effective acceleration gains, not firmware parameters.

The current code has diagonal Kp/Kd/Ga and a 21-input, two-hidden-layer NN with
three acceleration outputs. It lacks explicit attitude and hover-controller
memory. Current full execution uses an attachment-target fit that absorbs
orientation into translational error. The proposed origin-plus-attitude design
would replace that interpretation, not reuse those weights under a new label.

For M0, prefer shared horizontal parameters over an unconstrained cross-axis
gain matrix: the three whips provide little independent lateral excitation.
Use a low-parameter attitude response supervised by measured quaternions.
Its nominal input can be the controller's desired thrust-direction/yaw signal,
with a fitted orientation response time. The tracked-to-firmware mounting
rotation is unverified, so any use of firmware body axes requires explicit
calibration; do not silently identify the tracked Z axis with thrust direction.
The exact attitude equations and mounting treatment remain to be agreed.

Initialize the model using measured drone pose, estimated velocity and the
pre-hover command history. A steady hover includes controller compensation;
starting every maneuver with arbitrary zero controller memory can invent a
transient. Any effective bias or memory estimate must use pre-maneuver data
only. The onboard integral state is not directly logged here, so do not label
an estimated bias as a measured controller integral.

Keep the first drone NN small, bounded and strongly regularized. Its inputs
should describe current predicted tracking error, motion and causal command
history. Its initial output is zero. It must not depend on future measured
pose/cable state, trial identity or maneuver phase time as a memorization key.
Start with acceleration correction; add an angular correction only if explicit
attitude prediction errors justify that additional freedom. Supervise position
and orientation, and inspect uninterrupted recursive prediction, not only
one-step teacher-forced error.

## Cable physics and residual

Retain measured masses (drone 0.157 kg, cable assembly 0.018 kg), marker/cable
mass allocation, inextensible segment lengths, gravity, bending stiffness EI,
and internal bending damping Cb. Fix measured quantities rather than allowing
mass/length changes to absorb tracking error. EI and Cb are fit candidates,
subject to sensitivity and parameter-confounding checks.

Fit cable dynamics with the measured attachment boundary first. In combined
prediction, prescribe the predicted attachment boundary obtained from the
drone pose. The remaining cable state evolves through physics and its residual.

The latest candidate cable residual is specifically dissipative:

    delta_a_i = -D_i(q, v) v_i,  D_i >= 0 componentwise

It predicts state-dependent damping on free cable nodes; node zero receives
no direct NN correction. It can represent missing damping/drag in still air.
It cannot represent arbitrary elastic error or a purely energy-neutral nonzero
correction. Anisotropic damping can have a component perpendicular to velocity,
but remains constrained to dissipate energy. Thus it should not be described as learning every missing cable
force. Its current 2/s coefficient bound is a regularization choice, not a
measured drag constant; an acceleration field in its metadata is not an active
acceleration cap in dissipative mode.

Keep separate external drag at zero under the user's NN-only requirement; do
not reintroduce or initialize 0.3/s. Fit nominal cable terms first and freeze
them while fitting the residual. Consider shared/local tangent-normal damping
instead of independent world-axis/node coefficients for better symmetry and
fewer degrees of freedom, but this is a proposed architecture decision, not
an implemented change. If residual diagnostics show non-dissipative missing
effects, a damping-only NN will need reconsideration rather than a larger fit.

## Coupling choice that must remain explicit

The virtual point-mass/cable generator is mechanically coupled. The proposed
initial execution model can remain an effective *loaded-drone* response followed
by a cable model driven by its predicted attachment. This is one-way coupling
in execution. The fitted drone response statistically includes effects of the
installed cable; simply adding the simulated reaction force afterward can
count those effects twice.

This is a practical M0 approximation for the same setup and nearby maneuvers,
not a fully coupled identified drone/cable plant. Changing cable dynamics does
not automatically change the drone prediction in this architecture. Stronger
whips or substantially different cable loads can expose that limitation.

A physical two-way execution model would require a different force-accounting
contract, known reference-to-COM geometry, and identification that includes
cable reaction explicitly from the start. Nominal/residual fitting must then
be redone consistently. It cannot be obtained by adding F_cable/m to the old
loaded-drone surrogate. Choice between these execution models remains part of
the design discussion; the recommended time-limited starting point is the
explicitly labelled effective loaded-drone approximation.

## Timing, feasibility and observability

The agreed future rate is 30 Hz force decisions and 30 Hz FullState commands.
The physical simulation integrates more finely and resolves command boundaries
at multiples of 1/30 s. Neither the nominal 100 Hz OptiTrack rate nor 30 Hz
command rate is the onboard inner-loop frequency. Use actual historical packet
observations and known uncertainty during fitting, not an idealized new schedule.

Use one derivative-consistent P/V/A trajectory representation. Do not separately
smooth acceleration while leaving P and V inconsistent, or multiply exported
kinematic acceleration by mass/add gravity as if it were total force. The
FullState controller handles acceleration feedforward and gravity internally.

Reference and predicted-execution feasibility must be checked before PPO can
exploit unrealistic commands. Thrust, tilt, slew/rate and spatial limits need
verified vehicle values; a point mass alone cannot establish them. Evaluate
whip and recovery separately while retaining a continuous export and physically
feasible recovery. Do not give the policy future cable observations: planning
uses the agreed hanging estimate after hover, with hidden initial cable
uncertainty available only to the simulated evaluation.
